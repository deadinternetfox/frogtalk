🐳 Run your own onion Lilypad

A Lilypad is a FrogTalk node. Grow one with Docker, then turn on the hidden service: set FROGTALK_TOR_ENABLED=1, FROGTALK_ONION_URL, a SOCKS proxy, and FROGTALK_HOME_PAGE=tor. Generate a vanity frogtalk*.onion with the script.

git clone https://github.com/deadinternetfox/frogtalk
cd frogtalk && docker compose up -d
# then set FROGTALK_TOR_ENABLED=1 + your .onion

Operator guide
No central server. No owner.
“Federated” isn’t the same as decentralized. On some networks sold as decentralized, your identity and metadata still reach one company’s servers — even when you self-host. A FrogTalk onion node answers to no one but its operator.
Centralized “federation”
  • A flagship homeserver holds most accounts — a de-facto centre
  • An identity service maps you to email / phone / contacts, stored centrally
  • Metadata — who, when, from where — reaches central servers even from self-hosted instances
  • Server admins can read your media and files by default
FrogTalk over Tor
  • No central server. This onion node is independent — data lives here, not on someone’s hub
  • No identity broker. A nickname is the whole account — no email, no phone
  • Network and ownership privacy. Tor hides where you connect from; there’s no clearnet centre to subpoena
  • Client-side encryption. Signal-Protocol DMs + AES-GCM channels; the node stores ciphertext only
📇
frogtalk.app is a listing, not a landlord. The clearnet hub only publishes the public directory and release metadata — it can’t read your messages, hold your account, or switch this onion node off.

Privacy, not perfection

Tor hides network location; FrogTalk is still pre-alpha software. Do not rely on this node for high-risk communications.

  • JavaScript required for the full app today
  • WebRTC calls may not work in Tor Browser
  • Download clients from frogtalk.app — not from onion
  • Report issues via security page — not public exploits
